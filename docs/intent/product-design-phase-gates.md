# 产品设计阶段门禁

## 问题

原流程已经表达 `/pd → /s → /p → /b` 的顺序，但下游入口主要检查文件是否存在，没有要求证明：

- 产品设计开始前实际读取了项目公共产品上下文；
- 当前反馈与稳定产品约定的冲突已经处理；
- 本次增量已经形成并确认产品设计，而不是用通用产品总设计代替；
- 技术设计和实现没有静默补做产品决策。

这使 Agent 在获得“继续推进”授权后仍可能跨阶段，把已有公共原则误判为当前需求已经设计完成。

## 选择

保留现有 `/pd → /bl → /s → /p → /b` 主线，不增加平行流程或新的产品文档真相源。把同一门禁分布到
现有产物与入口：

- `AGENTS.block.md` 定义唯一阶段顺序和公共产品上下文优先级；
- `/pd` 产生公共产品上下文对齐记录和本次产品设计；
- Meegle 工作项保存这两项证据及产品经理确认状态；
- `/bl`、`/s`、`/p`、`/b`、`/mr` 在各自入口重新验证，不根据前一阶段“应该做过”进行推定；
- MR 合同机械检查“适用时引用齐全；不适用时说明原因”，不尝试用脚本判断产品语义是否一致。

## 否决方案

- 不依赖 Agent 自觉或会话记忆：换窗口、上下文压缩和协作者切换都会使承诺失效。
- 不在每个消费项目另建一份流程规范：会与 Workflow 发行源漂移。
- 不要求复制公共产品上下文到每个工作项：只记录本轮实际继承的约束与冲突，原文保持单一来源。
- 不让 CI 自动判断产品方案好坏：机器只验证可追溯性，产品语义仍由分阶段 review 负责。

# Meegle 工作项模板

一个工作项要同时指导**产品、研发、测试**三方的决策和动作。写不满这六段，说明需求还没想清楚 ——
不是格式没填完，是判断还没做。

复制下面的骨架到 Meegle 工作项描述里。

---

## 背景与目标

<为谁解决什么问题。做完之后什么变了。>
<一句话的成功标准：怎么算这件事做成了。不是「上线」，是「上线后什么指标/什么行为发生变化」。>

## 用户与场景

<谁在什么情况下会碰到这件事。给一个具体场景，不要写「用户希望更方便」。>

## 验收标准（可测）

<每条都要能写出对应的测试。测试同学直接照这里写用例，研发照这里判断做完没有。>

- [ ] <条件 → 期望结果>
- [ ] <边界情况 → 期望结果>
- [ ] <错误情况 → 期望结果>

> 写不出可测的验收标准 = 需求没想清楚，**不进开发**。
> 「体验流畅」「性能良好」不是验收标准；「P95 < 300ms」「失败时给出可重试的提示」才是。

## 边界与非目标

<明确这次不做什么。这是后面防止范围蔓延唯一的依据。>
<以及：哪些现有行为**不允许**被改变。>

## 影响面

| 维度 | 影响 |
|---|---|
| 模块 / 接口 | |
| 数据 / 存储 | <要不要迁移？能不能回滚？> |
| 上下游 | <谁在依赖它？要不要提前通知？> |
| 兼容性 | <老数据、老客户端怎么办？> |

## 风险与依赖

<挡路的东西：等谁的接口、等哪个决策、有什么已知不确定。没有就写「无」。>

---

## 状态流转约定

| 阶段 | 谁推进 | 前置条件 |
|---|---|---|
| 待评审 → 待开发 | 产品 | 验收标准可测、边界写清 |
| 待开发 → 开发中 | 研发 | 已有 `SPEC.md`（`/s` 产出，头部带本单号） |
| 开发中 → 待测试 | 研发 | MR 已开、CI 绿、自审通过 |
| 待测试 → 已完成 | 测试 | 验收标准逐条验过、回归结论已给 |

分支与 MR 都带本单号：`feat/PROJ-1234-xxx` / `feat(scope): 摘要 [PROJ-1234]`。

# /s —— 需求 → 可验证规格

## 输入

使用用户明确的需求、已批准对话、项目文档或任务记录；读取项目规范、相关代码与既有设计理由。现有实现用于核实影响，不替代需求。没有任务系统或固定规格文件不构成阻塞。

区分已确认行为与真实待澄清项，不臆造需求或优先级。关键输入不足时说明问题与影响，按项目审批和用户授权决定下一步。

## 产出

在项目已有需求或规格载体中写清：

- 目标：为谁解决什么问题，什么结果算成功。
- 可验证行为：条件与期望结果，包含适用的边界和错误路径。
- 边界与非目标：不做什么，以及必须保护的旧行为。
- 影响面：相关模块、接口、数据、上下游与兼容性。
- 待澄清：实际缺失的行为决定和能回答的人，不填空表。

需求有标识或链接时引用，不要求编号。按项目约定新建或更新载体；对话已足够承载明确规格时不另造文件。

## 规则

每条行为应可验证，不能用「体验流畅」代替可观察结果。需求变化更新其权威来源及受影响规格，不要求在特定系统先回写。这一步不实现代码；不重做产品定义、排期或内部技术选型。

行为和边界明确、必要决定已经确认后进入 `/p`；项目不需要单独规划的明确改动沿现有开发流程执行。

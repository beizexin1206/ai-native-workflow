# /t —— 用例化、回归、修 bug

## 分层覆盖：逐层判断，涉及就补

先读取项目测试规范和适用豁免；测试层次、依赖处理和运行时机按项目策略。根据改动判断实际涉及的边界，选择能证伪行为的验证层；不要求每个项目采用同一套层次：

- 单元、组件、接口、集成、E2E 等按项目实际策略选择，不填未涉及层的配额表
- 改了函数逻辑 → 单元；动了 API 契约 → 接口；跨模块或跨服务链路变了 → 集成；
  关键业务流程变化应验证真实路径，是否采用 E2E 由项目策略决定
- 前端改动要有自己的组件/状态测试，不能靠后端用例兑现

**已有代码缺测试时：**

1. 本次改动路径上的缺口**必须补**，否则这次行为根本没被验证
2. 路径之外的历史缺口列成清单写进回归结论，按项目规则及授权决定是否登记（缺哪层、哪段代码、什么风险），
   不塞进本次范围

## 三种场景

### 1. 新功能：验收标准 → 可执行用例

批准需求或规格中的可验证行为逐条变成测试。一条行为对不上任何测试 = 没验收。

覆盖不只是正常路径：**边界、错误路径、并发/重入**（如果适用）。
只有 happy path 的测试套件给的是虚假的安全感。

### 2. 修 bug：Prove-It 模式

1. **先写一个能复现 bug 的测试**，确认它 FAIL
2. 再修
3. 用同一个测试证明修好了
4. 跑项目规定的必要回归

自动化可复现的缺陷先用失败测试证明，再实现修复。项目明确豁免或只能在真实环境复现时，提供可核对的复现步骤、修复验证与限制，不把分析当测试通过。

发现缺陷时交给开发的是**一个失败的测试**，不是一句「这里有问题」。

### 3. 回归：按项目质量门执行，给结论

新需求不能只靠新用例证明没有回归。按影响面和项目策略执行回归；项目要求全量时跑全量，已通过且未失效的检查不为技能阶段重复执行。产出实际**回归结论**：

```
跑了 N 条，挂 M 条：
- <用例>：<为什么挂> → <修 / 是预期变更，已更新用例 / 既有问题及其实际依据>
```

这份结论用于项目实际审查请求的验证说明。**「测试通过」四个字不是结论**，
没说清跑了什么、挂了什么、为什么可以放，等于没验。

## 定位问题时

先保留证据（日志、失败输出、复现步骤），再动手。
按 复现 → 定位 → 简化 → 修复 → 防护 走，**找根因不打补丁**：
追踪同一个函数的所有调用方，只修 ticket 说的那条路径，兄弟调用方还是坏的。

同一个症状修第二次 → 停下来跑 `/ct`。

## Red Flags

- 测试是照着实现写的（实现改了测试就挂，但行为没变）
- 为了让测试变绿而改测试
- 回归「跑过了」但说不出跑了多少条
- 缺陷报告里没有可复现的最小步骤
- 只有单测，改动明明动了接口/链路/用户流程却没补对应层
- 前端改了但一条前端测试都没加
- 未核对实际影响的验证边界
- 明知本次改动路径无测试覆盖却继续改，把补测试推给“以后”
